`tech-writer-monolith` 에이전트가 한 콜에서 **작성·윤문·자체검증**을 끝내기 위해 사용하는 슬림 룰북. IT 기술 문서(개발 가이드·API 문서·테크 블로그·기술 리포트·RFC/설계서·업무 문서)에 최적화했다.

**적용 언어:** 한국어 · 영어 양방향. 패턴마다 `[KR]`·`[EN]`·`[KR/EN]` 태그로 적용 범위 표시.

**핵심 철학 — 구조는 자산이다**
이 스킬은 "구조를 없애는" 윤문기가 아니다. 기술 문서에서 **헤딩·불릿·번호 목록·코드블록·표는 권장 자산**이다. 우리가 제거하는 것은 *번역투·hype·모호성·중복·수동태 남용*이고, 우리가 **추가**하는 것은 *정확성·실행가능성·용어 일관성·전제 명시*다.

| 항목 | tech-writer 원칙 |
|---|---|
| 불릿·헤딩·번호목록 | **권장 — 가독성 자산** (제거하지 않음) |
| 목표 | 정확하고 실행 가능한 기술 문서 |
| 동작 | **작성(notes→문서) + 윤문 하이브리드** |

**Do-NOT (탐지·윤문 모두 제외, 원형 100% 보존):**
- 고유명사·제품명·버전·모델명·기관명, 수치·날짜·단위
- 코드·명령어·경로·환경변수·플래그·식별자(`camelCase`·`snake_case`·`kebab-case`)
- 코드블록(` ``` ` ~ ` ``` `) 내부 전체
- 인라인 코드(`` `code` ``) 내부
- URL·파일경로·정규식·JSON/YAML 키
- 큰따옴표 안 직접 인용, 라이선스·법률 조문, 수학·통계 표기
- 표준 약어(API·LLM·GPU·CLI·SDK·HTTP·CI/CD 등) — 첫 등장 풀이 후 약어 유지
- 옵션 플래그의 `--`, 수치 범위 `1—10`, 코드 내부 대시 (I-5 em-dash 정리의 carve-out)

> **Do-NOT 단 하나의 예외 — C-7(비밀정보 노출):** 코드블록·환경변수에 **실제** 비밀(AWS 키·토큰·비밀번호·사설키·실접속 문자열)이 박혀 있으면 플레이스홀더로 **치환(redact)**한다. 이때만 코드 내부 수정이 허용된다. 그 외 모든 코드·식별자·수치는 원형 보존.

**과윤문 가드:** 변경률 40% 초과 = 경고, 60% 초과 = 강제 중단·롤백. (기술 문서는 구조 재배치가 많아 일반 산문 윤문보다 임계를 높게 둔다. 단, 작성 모드는 변경률 산정 제외.)

**변경률 산식 (정본):** 문자 단위가 아니라 **산문 문장 단위**로 측정한다 (LLM이 문자 offset을 신뢰성 있게 못 세기 때문).

```
변경률 = (수정·삭제·추가된 산문 문장 수) ÷ (원본 산문 문장 수)
```

- **산문 영역만** 계산. Do-NOT 보존 구간(코드블록·표·인라인 코드·URL·식별자)은 분모·분자 모두에서 제외.
- **write 모드**: `n/a` — 변경률 산정 안 함. 등급은 자체검증 6항(변경률 제외)으로 채점.
- **hybrid 모드**: 기존 텍스트가 있던 구간에만 적용. 새로 작성한 절은 분모·분자에서 제외.
- **EN**: 동일하게 문장 단위 적용.
- 산정 방법을 `03_diff.json`의 `change_rate_method: "prose_sentence_ratio"`로 기록한다.

## A. 번역투 (Translation-ese) — 제거

| ID | 패턴 | 언어 | 심각도 | 처방 |
|---|---|---|---|---|
| A-1 | "~에 대해(서)" / "regarding / with respect to" | KR/EN | S2 | 목적격 직결("X에 대해 설명" → "X를 설명") / "X를 설명하면" |
| A-2 | "~를 통해/통하여" 남발 / "by means of, through the use of" | KR/EN | S2 | "~로", "~해서" / "by, with, using" |
| A-3 | "~에 있어(서)·~의 경우" / "in terms of, when it comes to, in the case of" | KR/EN | S1 | "~에서", "~할 때" / "X의 경우" → "X는"(주제)·"X에서"(범위)·"X일 때"(조건). 단 진짜 case 분기 열거는 보존 |
| A-7 | "가지고 있다" / have·make·perform + 명사 직역 | KR | S2 | 동사 환원("설정을 가진다" → "설정한다", "테스트를 수행한다" → "테스트한다") |
| A-8 | 이중 피동 "~되어진다/~되어집니다" | KR | S1 | 단일 피동 또는 능동("실행되어진다" → "실행된다") |
| A-9 | "~에 의해" 피동 / 불필요한 수동태 (by-구 + 행위자 생략 agentless passive) | KR/EN | S2 | 행위자를 주어로("시스템에 의해 처리" → "시스템이 처리") / "The request is handled by X" → "X handles the request". agentless: "It is recommended that you X" → "We recommend X / X", 절차는 명령형("The file is loaded at startup" → "Load the file at startup"). 단 행위자가 진짜 불명·무관하면(에러 서술) 수동 허용 |
| A-15 | 추상/지시 주어 또는 구체 무생물 주어 + 만능·사람동작·사역 동사 ("This shows/provides/allows/enables/makes it possible", "이 설정은 ~시킨다", "오류는 ~를 말해준다") | KR/EN | S2 | 구체 주어·결과로("이는 X를 제공한다" → "X를 쓰면 Y할 수 있다"). 사역·인격화는 도구격/조건절로("이 설정은 캐시를 비활성화시킨다" → "이 설정을 켜면 캐시가 비활성화된다", "오류는 ~를 말해준다" → "오류 메시지로 ~를 알 수 있다"). **보존 예외:** 반환한다·발생한다·포함한다류 자연 무생물 주어, 그리고 도구 자신의 동작 서술("로그가 자동 수집된다")은 정상 — 손대지 않는다 |
| A-18 | 명사 앞 ≥3어절 관형구 좌향 수식 | KR | S2 | 문장 분리 또는 후치("~를 설정하는 복잡한 절차" → "절차를 설정한다. 이 절차는…") |
| A-19 | 이중 조사 "~에서의/~으로의/~로부터의" | KR | S2 | 절·구로 풀기. 단순 ~의는 비대상 |
| A-20 | 직역체 명사화 "-tion/-ment/-ization" → "-션/-먼트" 음차 + 영어 동사 calque | KR | S2 | 한국어 동사·기존 역어로("디플로이먼트" → "배포", "이니셜라이제이션" → "초기화"). 동사 calque도: "Exception을 던진다" → "예외를 일으킨다", "에러를 발생시킨다" → "에러가 난다". 단 업계 표준(커밋·푸시·머지)은 유지 |
| A-21 | 복수 '-들' 직역 + 잉여 지시어·대명사 (영어 -s/주어 대명사 기계 이식) | KR | S3 | (1) 수량사·복수 한정사 동반 시 '-들' 삭제("모든 사용자들" → "모든 사용자"), 무정·추상명사('데이터들·설정들')는 거의 항상 삭제. (2) 지시 대상 자명하면 지시어 삭제·무주어화·연결("함수를 호출한다. 그것은 값을 반환한다" → "함수를 호출하면 값을 반환한다"). 한 문단 동일 지시어 3회+면 경고. **B-5와 구분:** B-5는 *모호한* 대명사(대상 복원), A-21은 *모호하지 않은* 잉여 표지(삭제) |

## B. 모호성·정확성 (Vagueness & Precision) — 기술 문서 핵심

| B-1 | 난이도 평가절하 "쉽게·간단히·그냥·당연히 / simply, just, easily, obviously" | KR/EN | S1 | 삭제. 독자에게 어려울 수 있음. 단계를 구체화로 대체 |
| B-2 | 모호한 양·정도 "많은·다양한·여러·적절한 / various, several, a number of, appropriate" | KR/EN | S2 | 구체 수치·조건으로("여러 옵션" → "세 가지 옵션: A, B, C") |
| B-3 | 모호한 지시 "위에서 / 아래에서 / 앞서 / above, below" 본문 참조 | KR/EN | S2 | 명시적 참조("3절 참조", 링크, 그림 번호) |
| B-4 | 막연한 시점·성능 "빠르게·곧·최근 / fast, quickly, soon, recently" | KR/EN | S2 | 정량화("p95 50ms", "v2.3부터", 날짜) 또는 삭제 |

| B-6 | 주장에 근거·예시 없음 (성능·보안·베스트프랙티스 단언) | KR/EN | S2 | 벤치마크·코드·출처 첨부 또는 "권장" 톤으로 완화 |
| B-7 | 과소 단언·헤지 적층 (B-6 반대축) "일반적으로 보통 대체로 ~한 편 / generally, in most cases, tends to be" 완충어 중첩, 또는 결정 자리에서 "장단점이 있다·상황에 따라 다르다"로만 종결 | KR/EN | S2 | 헤지어 1개 이하로 축약하거나 정량화("일반적으로 보통 빠르다" → "캐시 적중 시 5ms"). 판단 기준이 입력에 있으면 명시("읽기 위주면 A, 쓰기 위주면 B"), 없으면 날조 말고 `<!-- TODO -->`. RFC·리포트는 결론/권고 필수 |

## C. 코드·예제 결함 (Code & Example) — 기술 문서 전용

| ID | 패턴 | 언어 | 심각도 | 처방 |
|---|---|---|---|---|
| C-1 | 코드블록에 언어 태그 누락 (` ``` ` 뒤 언어 없음) | KR/EN | S2 | 언어 명시(` ```python `, ` ```bash `, ` ```json `) |
| C-2 | 플레이스홀더 비일관 (`<your-key>`·`YOUR_KEY`·`xxx` 혼용) | KR/EN | S2 | 한 컨벤션 통일 + 첫 등장 시 치환법 안내 |
| C-3 | 명령어·코드 본문에 평어로 박힘 (백틱 없음) | KR/EN | S2 | 인라인 코드로 감싸기(`npm install`, `--flag`) |
| C-4 | 출력 예시 없는 명령 (실행 후 무엇을 보는지 불명) | KR/EN | S3 | 기대 출력·결과를 별도 블록으로 |
| C-5 | 본문<->코드 불일치 — 식별자(본문 `getUser`, 코드 `fetchUser`) + 버전/수치(본문 "Node 18+", `package.json` `">=16"`) + 주석<->본문 동작(본문 "재시도 3회", 주석 `# retry 5 times`) | KR/EN | S1 | 동일 대상을 한 값으로 일치. Do-NOT 값(버전·식별자·주석) 자체는 보존이지만 *불일치*는 결함 — 어느 쪽이 정답인지 불명확하면 임의 변경 말고 `<!-- TODO: 불일치 확인 (본문 18 vs package.json 16) -->`. 주석은 코드 내부라 사실 변경 금지, 본문 측 교정 우선 |
| C-6 | 비결정적/위험 명령 경고 없음 (`rm -rf`, `DROP`, `--force`) | KR/EN | S1 | 경고 박스·되돌리기 불가 명시 |
| C-7 | 코드·예제·환경변수에 **실제 비밀정보** 하드코딩 (AWS 키 `AKIA…`, `sk-…`/`ghp_…` 토큰, 비밀번호, 사설키, 실제 접속 문자열) | KR/EN | S1 | 플레이스홀더로 치환(`<API_KEY>`·`AKIA…EXAMPLE`·`***`). **Do-NOT 예외: 이 경우에만 코드블록 내부 수정 허용.** 다른 형태의 가짜 비밀 날조 금지(명백한 placeholder만). 기존 노출 비밀은 "회전(rotate) 권고" 주석 |
| C-8 | 미완결·실행 불가 스니펫 (import/require 누락, 미선언 변수 `client`·`db`, 잘린 `...`으로 복사해도 안 돌아감) | KR/EN | S2 | 최소 완결 형태로 보강(필요한 import·선언 추가) 또는 "앞선 설정 가정" 1문장 + 전체 예제 링크. **새 API·인자 날조 금지** — 불명확하면 `<!-- TODO: 누락 import 확인 -->` |

## D. AI 관용구·hype (Signature & Hype) — 제거

| ID | 패턴 | 언어 | 심각도 | 처방 |
|---|---|---|---|---|
| D-1 | 결산 피벗 "결론적으로·따라서·요약하면 / In conclusion, In summary, Therefore" 남발 | KR/EN | S2 | 3회 초과 시 삭제. 기술 문서는 결론을 절 제목·요약 표로 |
| D-2 | "주목할 만하다·중요한 점은 / It's worth noting, Importantly, Notably" | KR/EN | S1 | 삭제 후 내용 직접 서술 |
| D-3 | "본질적으로·핵심적으로 / essentially, fundamentally, at its core" | KR/EN | S1 | 삭제 |
| D-4 | hype 어휘 "강력한·혁신적·획기적·매끄러운 / powerful, seamless, robust, cutting-edge, game-changing" | KR/EN | S1 | 구체 기능·수치로 환원("강력한 캐싱" → "TTL 기반 캐싱으로 DB 쿼리 70% 감소") |
| D-5 | "~의 세계로·~여정을 시작 / dive into, delve into, embark, unlock" + 2025–26 변종 "딥다이브·심층 분석·심도 있게 파헤치다·하나하나 뜯어보다 / take a deep dive, a comprehensive look at, let's unpack" | KR/EN | S1 | 직접 동작 동사로("살펴보자" → "설정한다"/"본 절에서는 X를 다룬다", "딥다이브해 봅시다" → "이 절에서는 캐싱 전략 세 가지를 설명한다") |

## 작성 모드 vs 윤문 모드

입력 성격으로 모드를 자동 판별한다.

- **작성 모드(write)**: 입력이 *개요·불릿 메모·요점·초안 조각*이면 → 완결된 기술 문서로 **작성**. 위 룰을 *생성 가이드*로 사용(처음부터 B·C·E·F·G를 충족). 변경률 산정 안 함.
- **윤문 모드(polish)**: 입력이 *완성된 글*이면 → A·D·H·I 위주로 다듬고 B·C·E·F·G 결함을 *교정*. 변경률 모니터링.
- **하이브리드**: 초안은 있으나 절·예제가 비어 있으면 → 빈 부분 작성 + 기존 부분 윤문.

판별 휴리스틱: 입력에 완결된 문장 비율 < 40%거나 "~에 대해 써줘/작성해줘/초안" 지시 → write. 그 외 → polish.

## 자체검증 체크리스트 (작성·윤문 후 자가 점검)

작성/윤문 직후 다음을 점검한다. 위반이면 해당 부분 수정.

1. **사실·코드·식별자·수치 100% 정확**: 원문/소스 대비 코드·명령·수치가 한 글자도 틀리지 않는가. 식별자 본문<->코드 일치(C-5)
2. **변경률**(윤문 모드만, 산문 문장 단위): 40% 이하인가 (60% 초과는 중단). **write 모드는 `n/a` — 이 항목 제외, 등급은 나머지 6항으로 채점.**
3. **구조 적절**: 절차는 번호 목록, 비교는 표, 헤딩 위계 정상(E)
4. **전제·용어**: 전제조건 명시(G-1), 용어·약어 일관(F-1·F-3), 미정의 용어 없음(G-2)
5. **잔존 S1 0건**: A-3·A-8·B-1·B-5·C-5·C-6·**C-7(비밀정보 노출 0)**·D-2·D-3·D-4·D-5·D-8·F-1·G-1·I-2
6. **실행가능성·안전**: 코드블록 언어 태그(C-1), 위험 명령 경고(C-6), **실제 비밀정보 미노출(C-7)**, 명령은 복사-실행 가능
7. **register·독자 일관**: 한 문서 내 경어/명령형 일관(H-5·G-4), 독자 레벨 유지

위반 시: 수정 → 재점검. 자체 루프 최대 1회. 미해결이면 결과 출력하되 summary에 "자가검증 미통과 N건" 표기.

## 등급 기준 (정본 SSOT — 전 문서가 이 정의를 참조)

이 등급 정의가 **단일 진실 원천**이다. SKILL.md·monolith·README·CLAUDE는 이를 복제하지 말고 인용한다.

- **A**: S1 잔존 0, S2 잔존 2 이하, 자체검증 통과 (윤문 7항 / write 6항)
- **B**: S1 잔존 0, S2 잔존 4 이하, 자체검증 (윤문 6항+ / write 5항+)
- **C**: S1 잔존 1~2 또는 자체검증 미달 — strict 모드 권고
- **D**: S1 잔존 3+ 또는 변경률 60% 초과(윤문 모드) — 중단·사람 검토 권고

> **write 모드 채점**: 변경률(2항)이 `n/a`이므로 분모가 6항이 된다. "7항 통과"는 "6항 모두 통과"로, "6항+"는 "5항+"로 읽는다.

### Strict 4축 <-> Fast 7항 매핑

`doc-clarity-reviewer`의 Strict 등급은 위 정의를 따르되, 아래 4축을 **추가 게이트**로 적용한다. Fast(자체검증)와 Strict(4축)가 같은 등급에 다른 의미를 주지 않도록 정렬한다.

| Strict 축 | Fast 자체검증 대응 | 비고 |
|---|---|---|
| 축1 결함 잔존 (S1 0 / S2 임계) | 5항(S1 잔존 0) | S2 임계는 등급표 기준(A=2, B=4)으로 통일 |
| 축2 실행가능성 (C-1·C-6·G-1·C-5·E-1) | 6항(실행가능성) | — |
| 축3 과윤문/구조위반 | — (Strict 전용 추가 게이트) | 구조 제거는 철칙 위반 → 단독 롤백 |
| 축4 명확성·자연도 | 7항(register·독자) | — |

> **score 개선폭**은 *제거 결함*(A·D·H·I)에만 적용한다. 보강 위주(C·E·G) 작업은 score가 크게 안 떨어져도 정상이므로 등급 강등 사유로 쓰지 않는다.
