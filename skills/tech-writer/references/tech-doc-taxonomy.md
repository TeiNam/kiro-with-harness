IT 기술 문서(개발 가이드·API 레퍼런스·README·테크 블로그·기술 리포트·RFC/설계서·업무 문서)에서 반복적으로 관찰되는 품질 결함을 9개 대분류 × 서브 패턴으로 정리한다. `doc-quality-detector`·`tech-doc-writer`·`doc-clarity-reviewer`가 공유하는 단일 진실 원천(SSOT). slim 룰북 `quick-rules.md`의 ID와 1:1 매칭.

각 패턴: (1) 정의, (2) 시그니처 예문(KR/EN), (3) 심각도(S1 결정적 / S2 강함 / S3 약함), (4) 처방.

**철학:** 구조(헤딩·목록·표·코드블록)는 제거 대상이 아니라 **권장 자산**이다. 이 분류 체계는 (a) AI·번역투 흔적 제거 + (b) 기술 문서 고유 품질(정확·실행가능·일관·전제) 보강 두 축을 함께 다룬다.

**적용 언어:** KR·EN 양방향. 각 패턴에 `[KR]`·`[EN]`·`[KR/EN]` 표시.

**심각도 운영 기준**
- **S1 결정적**: 한 번만 나와도 문서 신뢰를 깨거나 독자가 따라 할 수 없게 만드는 결함. 무조건 수정.
- **S2 강함**: 1~2회 허용, 반복 시 수정.
- **S3 약함**: 다른 패턴과 중첩될 때만 문제.

**Do-NOT (탐지·수정 모두 제외, 원형 100% 보존):** 코드블록 내부 전체, 인라인 코드, URL·경로·정규식·JSON/YAML 키, 식별자(camelCase·snake_case·kebab-case), 수치·날짜·단위·버전, 큰따옴표 직접 인용, 라이선스·법률 조문, 표준 약어.

> **Do-NOT 단 하나의 예외 — C-7(비밀정보 노출):** 코드블록·환경변수에 실제 비밀이 박혀 있으면 플레이스홀더로 치환(redact)한다. 이때만 코드 내부 수정이 허용된다.

## A. 번역투 (Translation-ese) — 제거

영어 구문을 한국어 어순·조사 체계로 무리하게 옮긴 흔적. 한국어 기술 문서 AI 글의 결정적 시그니처. EN 문서에서는 직역체·과형식 표현으로 대응.

### A-1. "~에 대해(서)" / "regarding, with respect to" [KR/EN] [S2]
- 정의: 영어 about/regarding의 1:1 매핑.
- 예: "캐싱에 대해 설명한다" / "Let me explain about caching"
- 처방: 목적격 직결 — "캐싱을 설명한다" / "This section explains caching"

### A-2. "~를 통해/통하여" 남발 / "by means of, through the use of" [KR/EN] [S2]
- 예: "API를 통해 데이터를 가져온다" (반복 시)
- 처방: "API로 데이터를 가져온다", "API를 호출해 가져온다" / "fetch data with the API"

### A-3. "~에 있어(서)·~의 경우" / "in terms of, when it comes to, in the case of" [KR/EN] [S1]
- 예: "성능에 있어서 중요하다" / "In terms of performance, it matters"; "타임아웃의 경우 재시도한다" / "in the case of a timeout"
- 처방: "성능에서 중요하다", "성능이 중요하다" / "Performance matters here". "X의 경우" → "X는"(주제)·"X에서"(범위)·"X일 때·X라면"(조건): "타임아웃의 경우 재시도" → "타임아웃이 나면 재시도", "프로덕션 환경의 경우" → "프로덕션에서는".
- 보존: 진짜 case 분기 열거(case 1 vs case 2 대비)에서는 유지.

### A-7. light verb 직역 "가지고 있다 / have·make·perform + N" [KR] [S2]
- 예: "강한 일관성을 가지고 있다", "테스트를 수행한다", "설정을 가진다"
- 처방: 동사·형용사 환원 — "일관성이 강하다", "테스트한다", "설정한다"

### A-8. 이중 피동 "~되어진다/~되어집니다" [KR] [S1]
- 예: "이 값은 자동으로 설정되어진다"
- 처방: "자동으로 설정된다" (단일 피동) 또는 "시스템이 자동 설정한다" (능동)

### A-9. "~에 의해" 피동 / 불필요한 수동태 (by-구 + 행위자 생략 agentless passive) [KR/EN] [S2]
- 예: "요청은 게이트웨이에 의해 처리된다" / "The request is handled by the gateway"; (agentless) "The config file is loaded at startup", "It is recommended that you set X"
- 처방: 행위자 주어 — "게이트웨이가 요청을 처리한다" / "The gateway handles the request". agentless는 행위자 복원 또는 명령형 — "The config file is loaded at startup" → (절차) "Load the config file at startup", "It is recommended that you X" → "We recommend X" 또는 "X".
- 보존: 행위자가 진짜 불명·무관하면(에러 서술 "Errors are logged") 수동 허용 — 과교정 금지.
- 경계: "It should be noted" 류 메타 표현은 D-2로 라우팅.

### A-15. 추상/지시 주어 또는 구체 무생물 주어 + 만능·사람동작·사역 동사 [KR/EN] [S2]
- 정의: 영어 무생물 주어 능동문을 1:1 직역해 (a) 지시대명사+만능동사(This shows/provides/allows/enables/makes it possible to/facilitate), 또는 (b) 구체 무생물 명사가 사람 동작 동사(말해준다·원한다·시도한다)·사역(~시킨다)을 취하는 패턴.
- 예: "이는 확장성을 제공한다" / "This provides scalability"; "이 설정은 캐시를 비활성화시킨다", "오류는 ~를 말해준다", "This framework makes it possible to reuse components"
- 처방: 구체 주어·결과로 — "이 구조를 쓰면 노드를 수평 확장할 수 있다" / "You can scale nodes horizontally with this". 사역·인격화는 도구격/조건절 — "이 설정을 켜면 캐시가 비활성화된다", "오류 메시지로 ~를 알 수 있다", "이 프레임워크로 컴포넌트를 재사용할 수 있다".
- **본 규칙 출처:** technical-writing.dev/sentence — "도구나 기술, 시스템을 행동의 주체로 사용하지 않아요", "능동형으로 표현해요". 즉 *도구를 능동 행위 주체로 세우는 것*을 금하는 게 A-15의 핵심이다.
- **보존 예외(이 스킬 자체 판단, 출처 페이지와 무충돌):** 반환한다·발생한다·포함한다류 자연 무생물 주어, 그리고 도구가 *행위 주체*가 아니라 자연 자동사·피동으로 서술되는 경우("로그가 자동 수집된다", "캐시가 만료된다")는 정상 — 손대지 않는다. 이들은 도구가 능동으로 *행동하는* 문장이 아니므로 본 규칙과 충돌하지 않는다.

### A-18. 명사 앞 ≥3어절 관형구 좌향 수식 [KR] [S2]
- 예: "사용자의 요청을 받아 검증하고 라우팅하는 복잡한 미들웨어"
- 처방: 문장 분리·후치 — "미들웨어가 사용자 요청을 받는다. 검증과 라우팅을 거친다."

### A-19. 이중 조사 "~에서의/~으로의/~로부터의" [KR] [S2]
- 예: "서버에서의 처리", "클라이언트로의 전송"
- 처방: 절·구로 — "서버에서 처리", "클라이언트로 전송". 단순 ~의는 비대상.

### A-20. 직역 음차 명사 "-tion/-ment/-ization → -션/-먼트" + 영어 동사 calque [KR] [S2]
- 정의: 이미 정착된 역어가 있는데 음차로 옮기거나, 영어 동사구를 한국어 관용을 무시하고 직역.
- 예: "디플로이먼트", "이니셜라이제이션", "컨피규레이션"; (동사 calque) "Exception을 던진다", "에러를 발생시킨다"
- 처방: 정착 역어 — "배포", "초기화", "설정". 동사 calque는 한국어 관용으로 — "예외를 일으킨다", "에러가 난다". 단 업계 표준 음차(커밋·푸시·머지)는 유지. (일반 원칙 출처: technical-writing.dev/sentence — "번역체 표현을 자연스럽게 수정하세요", "명사 대신 동사를 사용하세요". 구체 예 "Exception을 던진다"는 이 스킬 추가.)

### A-21. 복수 '-들' 직역 + 잉여 지시어·대명사 [KR] [S3]
- 정의: 영어가 형태적으로 요구하는 표지(복수 -s, 주어 대명사)를 한국어에 기계 이식하는 두 인접 패턴. 무생물 주어·피동과 중첩 시 두드러진다.
- 예: "이 미들웨어는 요청들을 받는다. 그것은 모든 헤더들을 검사한다. 그리고 그것은 그것을 다음 핸들러로 전달한다."
- 처방: (1) 수량사·복수 한정사 동반 시 '-들' 삭제("모든 사용자들이" → "모든 사용자가"), 무정·추상명사('데이터들·설정들')는 거의 항상 삭제. (2) 지시 대상 자명하면 지시어 삭제·무주어화·연결 — "함수를 호출한다. 그것은 값을 반환한다" → "함수를 호출하면 값을 반환한다". 한 문단 동일 지시어 3회+면 경고. 위 예문 → "이 미들웨어는 요청을 받아 헤더를 검사한 뒤 다음 핸들러로 전달한다."
- **B-5와 구분:** B-5는 *모호한* 대명사(대상 둘 이상)라 대상 명사를 복원하지만, A-21은 *모호하지 않은* 잉여 표지라 삭제·무주어화한다(정반대 처방).

## B. 모호성·정확성 (Vagueness & Precision) — 제거/보강

기술 문서의 핵심 품질 축. 독자가 따라 하거나 판단할 수 있어야 한다.

### B-1. 난이도 평가절하 "쉽게·간단히·그냥·당연히 / simply, just, easily, obviously" [KR/EN] [S1]
- 정의: 독자에게 어려울 수 있는 단계를 "쉽다"고 단정. 막히면 독자가 자책하게 만든다.
- 예: "그냥 토큰만 넣으면 됩니다" / "Simply configure the webhook"
- 처방: 부사 삭제 + 단계 구체화 — "Authorization 헤더에 `Bearer <token>`을 넣는다"

### B-2. 모호한 양·정도 "많은·다양한·여러·적절한 / various, several, appropriate" [KR/EN] [S2]
- 예: "여러 옵션을 지원한다" / "supports various options"
- 처방: 열거·수치화 — "세 가지 옵션(A·B·C)을 지원한다"

### B-3. 모호한 본문 참조 "위에서·아래에서·앞서 / above, below" [KR/EN] [S2]
- 예: "위에서 설명한 대로"
- 처방: 명시 참조 — "2.1절 설치 단계대로", 앵커 링크, 그림 번호

### B-4. 막연한 시점·성능 "빠르게·곧·최근 / fast, quickly, soon, recently" [KR/EN] [S2]
- 예: "빠르게 응답한다", "최근 버전에서"
- 처방: 정량화 — "p95 50ms 이내 응답", "v2.3 이상에서". 근거 없으면 삭제.

### B-5. 미정의 대명사 "이것·그것·해당 / it, this, that" [KR/EN] [S1]
- 정의: 지시 대상이 둘 이상이라 모호.
- 예: "이것을 설정하면 그게 적용된다"
- 처방: 대상 명사 복원 — "타임아웃 값을 설정하면 재시도 정책에 적용된다"

### B-6. 근거 없는 단언 (성능·보안·베스트프랙티스) [KR/EN] [S2]
- 예: "이 방식이 가장 빠르고 안전하다"
- 처방: 벤치마크·코드·출처 첨부, 또는 "권장"으로 톤 완화

### B-7. 과소 단언·헤지 적층 (B-6 반대축) [KR/EN] [S2]
- 정의: 의미 없는 완충어를 겹쳐 단언을 회피하거나, 결정이 필요한 자리에서 판단 기준 없이 "장단점이 있다"로만 종결해 독자가 판단·결정을 못 하게 만든다.
- 예: "일반적으로 보통 대체로 ~한 편이다" / "generally, in most cases, tends to be"; "장단점이 모두 있다·상황에 따라 다르다 / each has its trade-offs"
- 처방: 헤지어 1개 이하로 축약하거나 정량화 — "일반적으로 보통 빠르다" → "캐시 적중 시 5ms, 미스 시 80ms". 가짜 균형은 판단 기준 명시 — "장단점이 있다" → "읽기 위주면 A, 쓰기 위주면 B". 단 판단 기준이 입력에 없으면 날조 말고 `<!-- TODO -->`. RFC·리포트는 결론/권고 필수.

## C. 코드·예제 결함 (Code & Example) — 보강

### C-1. 코드블록 언어 태그 누락 [KR/EN] [S2]
- 정의: ` ``` ` 뒤 언어 미지정 → 신택스 하이라이트·복사 UX 손실.
- 처방: ` ```python `·` ```bash `·` ```json ` 등 명시.

### C-2. 플레이스홀더 비일관 [KR/EN] [S2]
- 예: 한 문서에 `<your-key>`·`YOUR_KEY`·`xxx` 혼용
- 처방: 한 컨벤션 통일 + 첫 등장 시 치환 안내("`<API_KEY>`를 발급받은 키로 교체").

### C-3. 명령어·코드가 평어로 박힘 (백틱 없음) [KR/EN] [S2]
- 예: "npm install 을 실행하세요"
- 처방: 인라인 코드 — "`npm install`을 실행하세요"

### C-4. 출력·결과 예시 부재 [KR/EN] [S3]
- 정의: 명령을 제시하나 성공 시 무엇을 보는지 없음.
- 처방: 기대 출력을 별도 블록으로. 검증 가능하게.

### C-5. 본문<->코드 불일치 — 식별자 + 버전/수치 + 주석<->본문 동작 [KR/EN] [S1]
- 정의: 산문에 적힌 값과 코드·설정·주석에 박힌 값이 어긋남. (a) 식별자: 본문 `getUser`, 코드 `fetchUser`. (b) 버전 드리프트: 본문 "Node 18+", `package.json`은 `"node": ">=16"`; 본문 "v2.3부터", 명령은 `pip install lib==2.1`. (c) 주석<->본문 동작: 본문 "기본 재시도 3회", 주석 `# retry up to 5 times`. 셋 다 복사-실행 재현 실패의 대표 원인.
- 처방: 동일 대상을 한 값으로 일치. **Do-NOT 값(식별자·버전·주석) 자체는 보존이지만 *불일치*는 결함** — 어느 쪽이 정답인지 불명확하면 임의 변경 말고 `<!-- TODO: 불일치 확인 (본문 18 vs package.json 16) -->`로 플래그. 주석은 코드 내부라 사실 변경 금지, 본문 측 교정 우선.

### C-6. 위험 명령 경고 부재 [KR/EN] [S1]
- 정의: `rm -rf`·`DROP TABLE`·`--force`·`git reset --hard` 등 비가역 명령에 경고 없음.
- 처방: 경고 박스 + 되돌리기 불가·전제 명시.

### C-7. 실제 비밀정보 하드코딩 [KR/EN] [S1]
- 정의: 코드·예제·환경변수·접속 문자열에 **진짜** 비밀이 박힘 — AWS 액세스 키(`AKIA…`), API 토큰(`sk-…`·`ghp_…`·`xoxb-…`), 비밀번호, 사설키(`-----BEGIN … PRIVATE KEY-----`), 실 DB 접속 문자열.
- 시그니처: 고엔트로피 문자열, 알려진 토큰 접두사, `password=`·`secret=`·`api_key=`에 더미가 아닌 실값.
- 처방: 플레이스홀더로 **치환(redact)** — `<API_KEY>`·`AKIAIOSFODNN7EXAMPLE`·`***`. **Do-NOT 단 하나의 예외**: 이 경우에만 코드블록 내부 수정이 허용된다.
- 주의: 이미 노출된 비밀은 문서만 고친다고 안전해지지 않는다 → "노출된 키는 즉시 회전(rotate)" 권고 주석을 남긴다. 명백한 placeholder 외의 가짜 비밀을 새로 지어내지 않는다.

### C-8. 미완결·실행 불가 스니펫 [KR/EN] [S2]
- 정의: 형식(C-1·C-3)은 맞지만 따라 하면 깨지는 코드 — import/require 누락, 미선언 변수(`client`·`db`), 잘린 스니펫(`...`)으로 복사해도 동작 안 함. 철칙 2(Runnable) 직결.
- 처방: 최소 완결 형태로 보강(필요한 import·선언 추가) 또는 "앞선 설정 가정" 1문장 + 전체 예제 링크. **새 API·인자 날조 금지** — 불명확하면 `<!-- TODO: 누락 import 확인 -->`.

## D. AI 관용구·hype (Signature & Hype) — 제거

LLM이 반복 산출하는 상투구·과장. 기술 문서 신뢰도를 직접 깎는다.

### D-1. 결산 피벗 "결론적으로·따라서·요약하면 / In conclusion, In summary" 남발 [KR/EN] [S2]
- 처방: 3회 초과 시 삭제. 결론은 절 제목("요약")·표·체크리스트로.

### D-2. "주목할 만하다·중요한 점은 / It's worth noting, Importantly, Notably" [KR/EN] [S1]
- 처방: 메타 표현 삭제 후 내용 직접 서술.

### D-3. "본질적으로·핵심적으로 / essentially, fundamentally, at its core" [KR/EN] [S1]
- 처방: 삭제.

### D-4. hype 어휘 "강력한·혁신적·획기적·매끄러운 / powerful, seamless, robust, cutting-edge, blazing-fast" [KR/EN] [S1]
- 예: "강력하고 매끄러운 인증 시스템"
- 처방: 구체 기능·수치로 — "TTL 캐싱으로 DB 쿼리 70% 감소"

### D-5. 진입 상투구 "~의 세계로·여정을 시작 / dive into, delve into, embark on, unlock" + 2025–26 변종 [KR/EN] [S1]
- 예: "캐싱의 세계로 떠나봅시다" / "Let's dive into caching"; (신변종) "딥다이브해 봅시다", "심층적으로 살펴보자", "심도 있게 파헤쳐 봅니다", "하나하나 뜯어보자" / "take a deep dive", "a comprehensive look at", "let's unpack this"
- 처방: 직접 동작 — "이 절에서는 캐싱을 설정한다" / "This section configures caching". "캐싱을 딥다이브해 봅시다" → "이 절에서는 캐싱 전략 세 가지를 설명한다".

### D-6. 결말 공식 "~할 때다·지금이야말로 / Now is the time, The future is" [KR/EN] [S2]
- 처방: 다음 단계·참고 링크로 닫기.

### D-7. 빈 전환구 "그럼 시작해봅시다 / Let's get started, Without further ado" [KR/EN] [S2]
- 처방: 삭제.

### D-8. 구조적 대조 안티테제 "X가 아니라 Y다 / not just X, it's Y" [KR/EN] [S1]
- 정의: 2025~2026 LLM 최상위 시그니처. 강조를 위해 부정-긍정 대조 틀을 반복하나 어휘는 평범해(D-4가 못 잡음) 빈 수사적 무게만 싣고 정보량 0. 한·영 양방향 빈발.
- 예: "단순한 캐시가 아니라 분산 일관성 계층이다", "옵션이 아니라 필수다" / "It's not just a library, it's a framework", "isn't about speed; it's about reliability", "more than just"
- 처방: 대조 틀 제거 후 긍정 절만 직설 — "단순한 캐시가 아니라 분산 일관성 계층이다" → "분산 일관성을 보장하는 캐시 계층이다", "It's not just fast, it's reliable" → "p99 지연 50ms를 유지한다". 독자가 X로 착각하기 쉬워 실제 오해를 교정할 때만 1회 허용.
- **D-4와 구분:** D-4=hype *어휘* 토큰(강력한·seamless), D-8=*수사 틀*(어휘가 평범해도 결함). 판정 기준: 긍정 절이 직설로 환원 가능한가.

### D-9. 독자 반응 유도 메타담화 [KR/EN] [S2]
- 정의: 독자의 인지 상태를 단정·연출하는 메타 표현. 정보량 없이 친근함만 연출.
- 예: "아시다시피", "말할 필요도 없이", "놀랍게도", "여러분도 궁금하셨을 텐데" / "As you know", "Needless to say", "Surprisingly", "You might be wondering"
- 처방: 삭제 후 내용 직접 서술. 독자가 무엇을 아는지·느끼는지 단정하지 않는다. (관련 출처: technical-writing.dev/sentence — "메타 담화를 최소화하세요". "아시다시피/As you know" 같은 독자-상태 단정 예는 이 스킬 추가.)

## E. 구조·탐색성 (Structure) — 보강 (제거 아님)

> 구조가 **없으면 추가**하고, 과하거나 비일관일 때만 정리한다.

### E-1. 절차가 산문 한 문단에 뭉침 [KR/EN] [S2]
- 예: "먼저 설치하고 그다음 설정 파일을 만들고 환경변수를 넣고 실행한다"
- 시그니처: 한 문단 뭉침 + **순서 메타부사 연쇄** — "먼저·다음으로·그다음·마지막으로 / First, Next, Then, Finally"가 3개+ 이어지면 짧은 문장으로 흩어져 있어도 번호 목록 전환 신호.
- 처방: 번호 목록으로 분해. 순서 의미 있으면 ol(1·2·3), 없으면 ul. 목록화하면 메타부사는 자동 제거된다("먼저 설치하고, 다음으로 설정한다" → "1. 설치한다 2. 설정한다").

### E-2. 헤딩 위계 점프·헤딩 없는 장문 [KR/EN] [S2]
- 정의: H2 → H4 점프, 또는 스크롤 두 화면에 헤딩 0개.
- 처방: 위계 정상화, H2/H3로 스캔 가능하게.

### E-3. 헤딩 콜론 부제 공식 "X: 완벽 가이드" 반복 [KR/EN] [S3]
- 처방: 명사구로 간결화.

### E-4. 비교/매핑을 산문 나열 [KR/EN] [S3]
- 정의: 옵션·파라미터·상태 코드 비교를 줄글로.
- 처방: 표로 전환.

### E-5. 문단·문장 과대 [KR/EN] [S2]
- 정의: 한 문단 5문장 초과, 한 문장 60자(EN 30단어) 초과.
- 처방: 분할.

### E-6. 구조 과잉 (E-1 역방향) [KR/EN] [S2]
- 정의: "구조는 자산" 철학의 역방향 가드. (1) 리스트 인플레이션 — 1~2문장이면 될 산문을 강박적으로 불릿화(항목당 평균 5단어 미만 명사 조각, 순서·병렬 관계 없는데 번호 매김, 콜론+불릿 3개로 한 문장 분해). 2025~2026 LLM 대표 티. (2) 과중첩·마커 비일관 — 3단계 이상 중첩, 같은 레벨 마커 혼용('-'와 '*'), 들여쓰기 폭 비일관.
- 예: "이 라이브러리의 특징:\n- 빠름\n- 안전\n- 사용 쉬움\n  - 정말 쉬움\n    - 진짜로"
- 처방: 관계 없는 짧은 불릿은 산문 1~2문장으로 병합("이 라이브러리는 의존성이 없고(번들 12KB) p99 5ms로 응답한다"). 진짜 절차(순서)·진짜 비교(축 2개+)·진짜 병렬 항목(3개+)만 리스트 유지. 3단계 초과 중첩은 별도 절(H3)·표로 평탄화. 마커 1종·들여쓰기 2/4칸 일관.
- **가드(철칙 3 보호):** 구조가 가독성을 *돕는* 게 아니라 *파편화*시킬 때만 결함. 판단 기준: 항목이 완결 문장이거나 표가 더 나으면 유지, 단어 조각이면 병합.

### E-7. 긴 문서 ToC·내비 부재 [KR/EN] [S2]
- 정의: H2 6개 이상 장문(가이드·RFC·리포트)에 상단 목차가 없어 전체 구조 파악·점프가 안 됨.
- 처방: 상단 목차 추가, 본문 상호참조는 앵커 링크로, 같은 개념 헤딩 표기 통일(F-1 연계).
- 보존: 짧은 README·블로그는 ToC 강요 안 함(YAGNI).

### E-8. 경고·팁이 평문에 매몰 (콜아웃 미격상) [KR/EN] [S2]
- 정의: 경고·주의·팁·중요·전제 같은 메타 정보가 일반 본문 속 평문으로 섞여 시각적으로 구분되지 않아 독자가 놓침.
- 예: "API 키는 한 번만 표시되므로 반드시 저장하세요"가 본문 중간에 평문으로 위치.
- 처방: 명시 단서어(주의·경고·반드시·팁·중요·전제 / Warning·Note·Tip·Caution·Important)나 기존 비격식 경고를 콜아웃 블록으로 격상 — `> [!WARNING]`·`> [!NOTE]`·`> [!TIP]`·`> 주의:`. 콜아웃 타입은 문서 전체 일관.
- **C-6과 분담:** 위험 *명령어*는 C-6, 비명령 경고(데이터 손실·요금 발생·보안 주의)는 E-8. 단서어 없는 문장을 의미만으로 경고로 판단하지 않는다(과발화 방지).

### F-7. 외래어 한글 표기 비표준·비일관 [KR] [S3]

## H. 능동·간결·시제 (Active & Concise) — 제거

### H-1. 문두 접속사 "또한·따라서·즉 / Also, Therefore, Thus" 5회+ [KR/EN] [S2]
- 처방: 대량 제거.

### H-2. "~할 수 있습니다" 남발 [KR] [S2]
- 예: "설정할 수 있습니다. 변경할 수 있습니다. 삭제할 수 있습니다."
- 처방: 단언·명령형 — "설정한다 / 설정하세요"

### H-3. 진행형 자동 매핑 "~하고 있다 / be -ing" [KR/EN] [S3]
- 처방: 단순 시제 환원 가능 시 환원.

### H-4. 군더더기 "~라는 것·~하는 것 / the fact that, in order to" + EN wordiness·명사화·시제 직역 [KR/EN] [S2]
- 처방: "to", 직접 동사로.
- EN 1:1 축약 매핑: in order to→to, due to the fact that→because, in the event that→if, has the ability to/is able to→can, a large number of→many, at this point in time→now, for the purpose of→to.
- 명사화 → 본동사: perform an installation of X→install X, make a configuration change→reconfigure, provide support for Y→supports Y.
- 영어 시제 직역 → 한국어 현재형: "반환할 것이다"→"반환한다"(일반 사실·동작), "되었었다/되어 왔다"→"되었다/이다". 미래 시제는 실제 로드맵 약속에만 유지.
- 경계: 'a large number of'의 모호 정도 측면은 B-2와 연계.

### H-5. 절차 시제·인칭 비일관 [KR/EN] [S2]
- 정의: "클릭한다 / 클릭하세요 / 클릭하면 됩니다" 혼용.
- 처방: 명령형으로 통일.

## I. 문서 위생 (Doc Hygiene) — 교정

### I-1. 미완성 마커 방치 "(TODO)·(링크)·(작성 중) / TBD" [KR/EN] [S2]
- 처방: 실제 내용·링크로 채우거나 명시적 주석으로.

### I-2. 깨진 마크다운 [KR/EN] [S1]
- 정의: 표 정렬 깨짐, 코드펜스 미닫힘, 헤딩 `#` 누락, 링크 문법 오류.
- 처방: 문법 교정.

### I-3. 이모지 장식 (기술 리포트·공식 문서) [KR/EN] [S2]
- 처방: 제거. 단 README 배지·캐주얼 블로그 톤은 허용.

### I-4. 강조 ** 남발 [KR/EN] [S3]
- 정의: 한 문단 3회 이상 bold.
- 처방: 핵심만 강조, 나머지 평어.

### I-5. em-dash(—) 구두점 과용 [KR/EN] [S2]
- 정의: 최신 LLM이 쉼표·괄호·콜론 대신 em-dash(—, U+2014)를 남발해 부연·전환·강조를 한 문장에 욱여넣음. 한 문장 2개+ 또는 한 문단 2회+ 삽입절이 시그니처. GPT-4o 이후 가장 정량 측정 가능한 구두점 AI 티.
- 예: "이 함수는 — 사실상 — 모든 요청을 처리한다", "설정 파일은 — YAML 형식이며 — 루트에 둔다 — 그리고 재시작이 필요하다" / "The token expires — by default — after one hour — so refresh it."
- 처방: 문맥 부호로 환원 — 부연은 쉼표/괄호, 전환은 마침표로 문장 분리, 강조 삽입절은 별도 문장. "이 함수는 — 사실상 — 모든 요청을 처리한다" → "이 함수는 사실상 모든 요청을 처리한다." 한 문단 1회 이내 권장.
- **Do-NOT carve-out:** 옵션 플래그(`--flag`)·수치 범위(`1—10`)·코드블록 내부는 건드리지 않는다.

### I-6. 깨진 내부 상호참조·앵커 [KR/EN] [S2]
- 정의: 문법은 맞으나 대상이 없는 내부 참조 — `[설치](#config-options)` 슬러그가 어떤 헤딩과도 매칭 안 됨, "3.2절 참조"인데 3.2절 없음, "위 표 참조"인데 표 삭제됨, 목차<->헤딩 텍스트 불일치. 윤문이 헤딩·절을 재배치하며 앵커가 깨지기 쉬워 이 스킬에서 특히 위험(자기유발).
- 처방: 참조 대상이 실재하는지 문서 내 대조 → 헤딩 텍스트로 앵커 재생성(GitHub 슬러그), 사라진 절·표 참조 교정·제거. 못 찾으면 `<!-- TODO: 참조 대상 누락 -->`. **윤문 중 헤딩을 바꿨다면 그 헤딩을 가리키던 모든 앵커도 함께 갱신.**
- **구분:** B-3(막연한 방향 참조)·I-2(마크다운 문법 오류)·I-1(외부 죽은 링크)와 다른 축 — 문법 valid + 대상 dangling. 핵심 내비 링크가 죽으면 S1로 승격 가능.

### I-7. 마크다운 접근성 — 이미지 alt 누락 + 불투명 링크 텍스트 [KR/EN] [S2]
- 정의: (1) 이미지 alt 누락·무의미 — `![](url)`이 비었거나 'image1·스크린샷·그림' 같은 무의미 값(기술 문서는 다이어그램·CLI 스크린샷 비중이 커서 스크린리더·로드 실패 시 정보 손실 큼). (2) 불투명 링크 텍스트 — '여기·클릭 / here, this, read more' 또는 노출된 생 URL이라 목적지를 맥락 없이 알 수 없음.
- 예: "![](./diagram.png) 설치는 [여기](https://docs.example.com/install)를 클릭하세요. 더 자세히는 https://docs.example.com/api 참고."
- 처방: (1) alt를 이미지가 전달하는 정보로 — "![아키텍처: 클라이언트 → API 게이트웨이 → 인증/주문 서비스 → PostgreSQL](./diagram.png)". 순수 장식은 빈 alt 허용. (2) 링크 텍스트를 목적지 서술 명사구로 — "[설치 가이드](...)를 참고한다". 생 URL은 의미 텍스트로 감쌈(명령 안 URL이면 인라인 코드 유지). 같은 목적지 링크 텍스트는 문서 내 일관.
- 구분: B-3(본문 위치 참조)과 다른 축 — 마크다운 링크 라벨의 불투명성.
